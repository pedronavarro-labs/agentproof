# Google identity for the approval pilot

This optional integration uses **two separate Google identities**. The agent process obtains a Google-signed ID token from its attached or impersonated Google Cloud service account. The reviewer signs in interactively with a Google account through a Desktop OAuth client in their own terminal and browser. The first is a workload identity; the second is a person permitted by an exact Google `sub` allowlist. Google API OAuth scopes (`openid email`) are used only for reviewer sign-in. AgentProof's `tickets:read` and `tickets:write` grants are host policy, not claims in Google's ID token.

The [Google ID token guidance](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token) recommends verifying the signature, issuer and audience using its client library and using `sub` as the stable identifier. The [Desktop OAuth flow](https://developers.google.com/identity/protocols/oauth2/native-app) supports a system browser and loopback redirect with PKCE. AgentProof uses those libraries, requires a new nonce and recent authentication for each approval, checks `email_verified`, and never persists refresh tokens. It does not use Google's `tokeninfo` debug endpoint to establish trust.

## One-time setup outside the repository

1. Create a Google Cloud project and configure its OAuth consent screen for a Desktop application. Add the reviewer Google account as a test user if the consent screen is in testing. Download the OAuth Desktop client JSON to a private local path; **do not commit it**. Only `openid` and `email` are requested.
2. Create a dedicated Google Cloud service account for the agent. Run the guarded server in an environment where the service account can obtain a Google-signed ID token through Application Default Credentials. Prefer attached workload identity or short-lived impersonation rather than a downloaded private key. Obtain its stable numeric `sub` from a verified ID token or the Cloud service-account unique ID and set it as `AGENTPROOF_GOOGLE_AGENT_SUB`.
3. Install the optional dependencies: `python -m pip install -e '.[google]'`.
4. Set `AGENTPROOF_GOOGLE_CLIENT_CONFIG` to the private Desktop client JSON path. Run `python examples/mcp-runtime/review_google.py --whoami` on your own computer and complete Google login. Copy the returned Google `sub` to a private `AGENTPROOF_GOOGLE_REVIEWER_SUB` setting. This bootstraps a reviewed allowlist without putting an email address or ID in source control.

The guarded server needs `AGENTPROOF_IDENTITY_PROVIDER=google`, `AGENTPROOF_GOOGLE_AGENT_AUDIENCE` (an application-specific audience string), `AGENTPROOF_GOOGLE_AGENT_SUB`, `AGENTPROOF_APPROVAL_DB`, and `AGENTPROOF_AUDIT_DB`. The reviewer needs `AGENTPROOF_GOOGLE_CLIENT_CONFIG`, `AGENTPROOF_GOOGLE_REVIEWER_SUB`, and the **same private** `AGENTPROOF_APPROVAL_DB` path. Start `python examples/mcp-runtime/verified_server.py` as the MCP stdio process; after a write returns `approval_required:<id>`, run `python examples/mcp-runtime/review_google.py <id>` in a separate terminal. Inspect the exact structured arguments and sign in with the allowlisted Google account. Retrying that exact write consumes the approval once.

The example stores a ticket in memory; it does not modify any Google account data. No Google credentials or OAuth client configuration are bundled. A personal Google login alone does **not** grant an agent a service account, deploy a guarded host, or prove that a reviewer has MFA. The trusted host must isolate its service account from agent-controlled tools, protect the SQLite databases and ensure that every real side effect passes through the guard. This remains a local MCP `stdio` pilot, not a general Google Sign-In service, an HTTP MCP gateway, or an external security audit.
