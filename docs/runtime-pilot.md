# Experimental runtime pilot

The `RuntimeGuard` library demonstrates a narrow enforcement point at tool dispatch. A host application supplies an AAM, a trusted registry of handlers and their operation types, and scopes obtained independently of the agent's tool-call arguments. Each `call(name, arguments)` is checked before dispatch. A declared read with matching operation and scopes is dispatched; unknown tools, mismatched bindings, missing scopes and all writes are denied. Audit events contain a tool name, decision and reason, never arguments or return values.

Run `python examples/runtime-demo/demo.py` after installing the package or setting `PYTHONPATH=src`. The synthetic host registers `tickets.get` and `tickets.update`. The AAM grants only `tickets.get` and `tickets:read`. An attempted `tickets.update` is rejected and the ticket state stays `open`. No external service or actual MCP client is involved.

This is **not** a full MCP protocol implementation. The next integration would place the gate at a genuine MCP `tools/call` boundary and obtain the authenticated principal and granted scopes from the host's auth layer. It must bind requests to an independently checked manifest revision and send immutable, privacy-conscious evidence to an audit store. An approval verifier for writes must be separate from agent-controlled arguments. Until then, every write fails closed.

The host can bypass the gate by calling handlers directly, using another MCP connection, or giving the agent separate credentials. A compromised host can lie about scopes or tool operation types. An AAM author can misrepresent allowed actions; the current static validation does not authenticate manifest provenance. Production use requires exclusive routing, independently verified identity/scopes, trusted approval and audit storage, and review of the actual adapter. The demo establishes only that **this local dispatch path** blocks the synthetic write before its handler executes.
